## Changes Required by Official

Only these three executable-source changes were made:

1. Removed the trailing comma after `BLUE` in `enum Color`.
   Official rejected the closing `};` with `unexpected token: }` at line 29.
   The other enum, its values, and the semicolon after the first enum remain.

2. Split the immediately invoked anonymous function into assignment and call.
   Original:
   ```gs2
   temp.h = function (x) { return x * 2; }(21);
   ```
   Compiled:
   ```gs2
   temp.immediate = function (x) { return x * 2; };
   temp.h = temp.immediate(21);
   ```
   Official reported `missing semicolon` at the original line 448. Wrapping
   the lambda in parentheses also failed with `unexpected token: function`.
   The split preserves the intended calculation but adds a temporary variable;
   it is not a claim of identical bytecode to a direct invocation.

3. Supplied the required search-value argument to the array builtin:
   ```gs2
   // Original
   temp.idxs = temp.o.indices();
   // Compiled
   temp.idxs = temp.o.indices(2);
   ```
   Official reported `not enough parameters for array.indices(object)` at
   line 413. The value `2` is the test's search value: this operation finds
   array indexes containing that value. It does not enumerate object keys.

No functions were removed. No labeled loops were rewritten. No other builtin
calls were changed. The original source and all failed attempts remain saved
in the repository under `tests/gs2-feature/evidence/`.

## Our Compiler's Support

- GS2 parsing uses the shared ANTLR4 grammar, not the GS1 grammar.
- Trailing commas remain accepted in enums, array literals, and call arguments.
  Official-backed tests prove they do not change the corresponding output.
  Restoring `BLUE,` in the full corrected script also leaves our output unchanged.
- Dotted references to previously declared enums, such as `Color.GREEN`, now
  emit their numeric constants instead of runtime property lookups.
- Named `break` and `continue` now parse and target the named enclosing loop.
  Focused while/for probes match official bytes. Missing or out-of-scope loop
  labels raise an error, including references across a lambda boundary.
- The valid one-argument `indices(value)` call now uses the dedicated official
  opcode. Its focused probe matches all 89 bytes.
- Anonymous function declarations and invocation through a variable compile.
  The direct immediately invoked lambda form is not a verified local feature;
  its existing adapter can drop the invocation. Use the supplied split form.
- The complete corrected script compiles locally, including the labeled loops.

## Corrected Script Parity: Verified

The complete corrected script now matches official after accounting only for
generated anonymous-function IDs and the function-table ordering those IDs
cause. This is verified against three complete official captures, including
a fresh MCP compilation on 2026-09-12. Every function entry address matches.
The entire 5,843-byte instruction segment is byte-for-byte identical, including
all jump targets and string indexes. Event flags are also identical. Tests
compare the complete string table after normalizing generated lambda IDs;
ordinary function names, their ordering, and all other strings remain exact.

Our deterministic lambda names are `function_100_1`, `function_100_2`, and
`function_100_3`. Consequently our file is 7,857 bytes, six bytes shorter than
the delivered official file: three generated names appear in two tables and
each has a one-character-shorter ID. This is not a byte-for-byte file match,
but there are no remaining instruction, address, or non-generated-name
differences for this corrected script.

The compiler fixes cover variable caching and native builtin cache isolation,
constant folding and number encoding, builtin argument order/conversions,
foreach stack cleanup, switch exits/continue, ternary and loop jumps, range
flags, object creation, and public/qualified function-table ordering.

There is also an official reproducibility detail: a second compilation of
the exact same source produced different anonymous names (`function_1040_*`
instead of `function_1038_*`) and corresponding function-table ordering.
Both official runs have identical event-flag and instruction segments.
After normalizing only generated name IDs and function-table order, their
remaining segments match. The delivered file is the first successful result,
with the checksum above; it was not normalized or altered.
